**这组 C2 数字在算术上自洽，但在语义上是异常的。**  
`122880` 没问题；`100% / 0 / 0` 不是「策略已经写满、没有攻击面、也不再依赖 LLM」，而是抽取把**兜底语义写成了通配规则**之后，C2 的分母被吃光了。

---

## 先把四个数字分开看

| 指标 | 这次 `out-ds` | 离线 IR（人工折叠的 24 条） | 是否异常 |
| --- | --- | --- | --- |
| 状态空间总数 | 122880 | 122880 | 否 |
| V_explicit | 122880（100%） | 约 121428（98.82%） | **是** |
| V_danger | 0 | 8（0.01%） | **看起来像好结果，来源不对** |
| V_deferred | 0 | 约 1444（1.18%） | **是，而且最不该为 0** |

`122880 = 6×10×4×2⁹`，就是词表宇宙，三者之和也等于它。计数器没有算错。

C2 的划分是：

```111:122:smt_completeness/analysis/coverage.py
    for state in all_states():
        if _any_rule_matches(policy, state):
            explicit += 1
        elif is_default_allow(state):
            danger_states.append(state)
        else:
            deferred += 1
```

要点：**只要任意一条 deny / challenge / allow 命中，该状态就进 V_explicit**。  
它不看判定对不对，也不看规则是否通配。`V_danger` / `V_deferred` 只统计「一条规则都没碰到、只能走编译器默认」的剩余。

因此：出现一条「永远命中」的规则，C2 会立刻变成 `100% / 0 / 0`。

---

## 根因：至少两条 `must_challenge` 条件为空

IR 里列表为空表示该维度通配（don't care）。五个维度都空，就是**命中全部 122880 个状态**。

同一次运行导出的 `out-ds/policy.smt2` 里，Challenge 层被编译成：

```48:49:out-ds/policy.smt2
(let (($x141 (or ... true true)))
(let ((?x162 (ite $x141 1 (ite $x204 0 (ite (and $x258 $x58 $x145) 0 1)))))
```

末尾两个 `true` 就是两条空条件的 `must_challenge`。Challenge 恒真之后：

1. 每个状态都「被规则覆盖」→ **V_explicit = 122880**
2. 再没有「无规则」状态 → **V_danger = 0、V_deferred = 0**
3. 判定退化成：`Deny if 命中拒绝 else Challenge`（Allow 与默认放行分支成为死代码）

这和文档 §6.3 的本意相反。§6.3 的「没有已有策略完整匹配时……其他情况进入 LLM 兜底」应当留在**编译器默认**里，用来定义 V_deferred；离线 IR 也没有把它写成一条规则。DeepSeek 抽取时，很像把这段默认话术收成了「无约束的必须进一步判断」。

自检拦不住：`vacuous` 只删**永不命中**的规则，不删**永远命中**的规则。空条件全部命中，自检显示通过（67 条、恒假=[]）。

抽取 prompt 也很薄，schema 又允许空列表，模型容易把「其余都要再判断」写成通配 Challenge。

---

## 为什么不能把它读成「已经完备」

同一份报告里，其它指标和「100% 覆盖」互相打架：

| 旁证 | 这次 | 离线基线 | 说明 |
| --- | --- | --- | --- |
| 威胁覆盖 | 7/18（38.9%） | 12/18（66.7%） | 覆盖率更差，不是更安全 |
| C3 重叠 | 82232 | 约 5052 | Challenge 恒真时，重叠 ≈ 全部 Deny 体积 |
| 冗余 | 47/67 条 | 3 条量级 | 大量规则被通配 Challenge/更严 Deny 盖住 |
| 敏感度倒挂 | 9544 | 文档预期远小于此 | 例如读 `agent_memory` 为 Challenge，读更敏感的 `private_data` 为 Deny |
| TINV-CRED-18 等 | 仍是需求缺失 | 同样未覆盖 | 凭据写入等该 Deny 的点并未被补上 |

尤其是 **V_deferred = 0 与文档 §9 直接冲突**：长期策略故意表达不了内容级授权，离线测量应留下约 1444 的 LLM 依赖残差。残差被抹成 0，只说明度量被通配规则失效，不说明词表已经够用。

**V_danger = 0 也不是补全闭环那种 0。**  
正规补全是给那 8 个默认 Allow 点加 **Deny**，V_deferred 仍约 1444。这次是 Challenge 把默认 Allow 连同整片默认 Challenge 一起吞掉。那 8 个点从 Allow 变成 Challenge，格上是收紧了，但手段是「全域再判断」，不是补洞。

更关键的误读：运行时仍有大量 Challenge。Challenge 恒真下，Deny 约 82232，其余 **40648 个状态 D=Challenge**，照样要 LLM 兜底。C2 的 `V_deferred` 标签是「对 LLM 的依赖度」，这里却报 0——因为它只统计**默认** Challenge，不统计**显式规则给出的** Challenge。

## 读这段报告时的口径

- **122880**：正常，宇宙大小。
- **100% / 0 / 0**：计数正确，解释错误；是抽取过宽，不是需求写完了。
- 不要对外说「无攻击面、无 LLM 依赖」。应说：出现通配 `must_challenge`，C2 饱和，指标失效；安全结论要看威胁缺口、C3/C4、单调性，而不是看这三行百分比。

若要这次 LLM 抽取的 C2 重新有意义，需要在抽取或自检里禁止「条件全空」的判定规则（或禁止把 §6.3 默认兜底收成 IR 规则），再重跑。
