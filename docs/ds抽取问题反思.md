**结论先说：**这次跑偏不是分析器算错，而是「文档语义 → IR」这一层几乎没有防护。优化应做成**分层拦截**，并且**不要改 C2 的定义、不要用覆盖率阈值一刀切、不要把通配规则静默删掉**——那三类改法都会制造新的假安全。

下面按「问题出在哪 → 三条路线 → 推荐落地（含明确不做）→ 新风险」说明。

---

## 1. 当前系统为什么会把原文抽歪

设计里本来有几道闸，实现时被裁掉或留空了。

| 设计意图 | 现状 | 后果 |
| --- | --- | --- |
| 分段抽取（§3/§4/§5 各 5–15 条） | 整篇文档一次塞进一句 prompt | 模型把 §6.3 默认兜底、§4、§9 限制搅在一起 |
| 词表封闭 + 失败重试 | 只校验 flag 是否在名单里 | 空条件合法，通配 Challenge 一次过 |
| 自检：非恒假、id 唯一 | 只拦「永不命中」 | 恒真规则是反面，放行 |
| 回译一致率作参考 | 未做 | 没有「规则是否还像原文」的信号 |
| 人工审核字段 | 默认 `auto_approved` | 67 条直接进分析 |
| 抽取 IR 落盘 | 只写 report / smt2 | 人无法对照原文审规则，只能从 SMT 反推 |
| §6.3 默认由编译器实现 | 未告诉模型「禁止写成规则」 | 默认被收成 IR 后，C2 定义性失效 |

`Condition` 的空列表是**有意的通配**，离线 IR 里 `{flag_true: [destructive]}` 这种单维宽规则是对的。问题不是「通配」本身，而是**判定规则五维全空**（或若干条合起来等于全集），把编译器默认吞掉。

instructor 的 `max_retries=3` 只在 pydantic `ValueError` 时重试。现在空条件不会报错，所以重试机制帮不上忙。

## 2. 三条路线（取舍）

**路线 A — 只加硬约束（改动小）**  
判定规则至少要有一个条件文字；自检增加「恒真」；抽取结果写成 `extracted_ir.yaml`。  
优点：离线 24 条不受影响，假阳性极低。  
缺点：挡不住「六条很宽的 Challenge 拼成全集」，也挡不住把 §6.3 意译成一条「几乎通配」的规则。

**路线 B — 分层防护（推荐）**  
A 的硬约束 + **章节隔离抽取** + **报告质量闸**（C2 异常只告警、必要时拒绝进入补全）+ 把默认语义明确划给编译器。  
优点：对准这次故障模式，且和 MVP 设计 M1 一致。  
缺点：章节切分对「不是 OpenClaw 结构」的文档要有退路。

**路线 C — 再加第二模型回译 / 对拍 golden IR**  
B 之上用 LLM 把规则译回中文，或强制接近 24 条 fixture。  
优点：纸面更严。  
缺点：裁判模型会护短；对拍 fixture 会把抽取器做成「复读离线 YAML」，失去评测自然语言的意义。

建议做 **B**，把 C 里的回译只做成**参考分**（设计里已有这句话），不要当准入。

## 3. 推荐落地：五层，每层只做一件事

### 第 0 层：先分清「谁拥有默认语义」

判定函数里这两行是**编译器的**，不是抽取目标：

- 无规则 ∧ 无 flag ∧ read/list ∧ local → 默认 Allow  
- 其余无规则 → 默认 Challenge  

文档 §2 资源定义、§6 执行顺序、§7 LLM 守则、§9 能力上限，也不应变成 `mandatory_deny / must_challenge / may_allow`。IR 里已有 `resource_def`、`limitation`，但抽取从未被要求用它们，模型就把一切都收成判定规则。

**不做：** 改 `decide_py` / C2 公式去「消化」通配规则。那会让指标看起来正常，问题藏进语义里。

### 第 1 层：Schema + prompt（防生成）

对 `kind ∈ {mandatory_deny, must_challenge, may_allow}`：`operation / resource_class / target_zone / flag_true / flag_false` **至少一处非空**。用现有 pydantic `ValueError` 文案写成给模型的修复指令，instructor 会自动重试——与非法 flag 同一机制。

Prompt 需要写死三条（现在只有「用词表、给溯源」）：

1. 只从「必须拒绝 / 必须进一步判断 / 可以允许」抽判定规则。  
2. **禁止**把「没有已有策略匹配时……」写成规则。  
3. 缺省维度 = 通配，但禁止五维全空；单维（例如只约束 `destructive`）是允许的。

附 1 条正例、1 条反例即可，不要把整份 `ir_openclaw.yaml` 当 few-shot，否则模型会抄 fixture 而不是读文档。

**新问题怎么避：** 不要要求「每个维度都填」。否则 `R3.2.1` 这种「破坏则拒绝、不管资源和区域」会被误杀，策略会假性变窄，MustAllow / 威胁覆盖一起坏。

### 第 2 层：按章节抽取（防串章）——杠杆最大

这是设计写了、代码没做的 M1。对 OpenClaw 这类文档：

| 章节 | 允许产出的 kind | 否则 |
| --- | --- | --- |
| §3 | 仅 `mandatory_deny` | 重试或丢弃该条 |
| §4 | 仅 `must_challenge` | 同上 |
| §5 | 仅 `may_allow` | 同上 |
| §2 | `resource_def`（不进入 D） | 不参与 C2 |
| §6.3 / §7 | **不抽取规则** | 默认留给编译器 |
| §9 | `limitation` | 进报告附录，不进 D |

合并时用 `R3.* / R4.* / R5.*` 前缀，避免 67 条 `R001` 这种无溯源编号。

**新问题怎么避：**

- **跨节限定语**（§5 末尾「若带更高风险则走 §3/§4」）不要让 §5 抽取器自己减；那是 `must_allow()` 已有的语义。分段后若模型在 §5 规则上乱加 `flag_false`，反而会把 floor 划窄。  
- **非 OpenClaw 文档**不要硬绑 `##` 号。无匹配章节时退回「整篇 + 第 1 层约束」，并在报告里写 `extraction_mode=flat`。  
- 分段不要并行乱序合并丢规则；按章节稳定排序。

### 第 3 层：自检扩成「恒假 ⊕ 恒真」（防漏网）

在现有 `vacuous` 旁增加**语法层**检测，不要用「命中状态占比 > 10%」这种阈值：

- `tautology_rule_ids`：判定规则条件全空（或 Z3 上 `match_expr ≡ True`）。  
- `kind_covers_universe`：某一 kind 的析取为恒真（这次就是 Challenge 层 `true true`）。  

这两项应使 `self_check.ok = False`，CLI **不写分析报告当成功**（与现在重复 id / 恒假同等待遇），把失败原因和规则 id 打进 stderr / 一份 `extract_qa.json`。

**新问题怎么避：**

- **不要静默删除**恒真规则再继续跑。删除后 C2 会「好看」，等于系统替模型改了策略，审计链断了。  
- **不要用体积阈值**（例如覆盖 > 50% 就拒绝）。`flag_true: [destructive]` 合法覆盖一半宇宙；`recon_scan` 等同理。阈值会逼模型把宽规则拆碎或乱加无关维度。  
- 恒真检测必须**只作用于判定 kind**；`limitation` 可以没有状态谓词。

### 第 4 层：质量闸只告警、并拦住补全（防假收敛）

分析仍可跑（便于看 C3/C4/威胁），但报告 §2 应增加**抽取质量**而不是假装完备：

- `V_explicit == 100%` 或 `V_deferred == 0` → 警告：「可能把默认 Challenge 收成了规则；C2 不宜对外解读为完备。」  
- 冗余率过高、C3 重叠接近 Deny 体积 → 旁证。  
- 若这些警告触发，**默认跳过 `run_completion`**（或必须 `--force-complete`）。否则会像这次一样：`V_danger=0` 被当成补全已收敛。

**新问题怎么避：** 不要把 `V_deferred==0` 做成硬失败——若将来文档真的用显式规则铺满空间，应能过；所以这是警告 + 补全闸，不是自检否决。真正否决留给第 3 层的恒真。

### 第 5 层：可审产物（防「只有百分比」）

`write_reports` 同时写出 `extracted_ir.yaml`（过自检的 IR）。这是这次最缺的工程能力：没有 YAML，就无法把 67 条和 §3/§4/§5 逐条对读。

可选、且默认关闭：回译一致率（把每条规则模板渲染成中文，和 `source_anchor` 做粗匹配），只进报告参考分。不要用第二个 LLM 当法官。

## 4. 明确不要做的事（比要做的更重要）

1. **不要改 C2 定义**（例如「通配规则不计入 explicit」）。指标一改，历史报告与设计文档全部失效，且等于承认「有规则也可以当没规则」。  
2. **不要拿 24 条 fixture 当抽取金标准。** 手册已写「不必等于 24 条」。对拍会让 LLM 路径失去评测价值。最多在 `tests/` 里对**人造坏 IR**（空 Challenge）做回归，不要对直播抽取断言条数。  
3. **不要在补全循环里「修抽取」。** 补全只关默认 Allow 的危险面；用它去补救通配 Challenge，会把错误 IR 焊死成更多 Deny。  
4. **不要上人工审核 UI 当第一依赖。** 设计已砍掉；先做到「坏 IR 进不了成功路径 + YAML 可审」。  
5. **不要为 DeepSeek 单开一套更严规则、OpenAI 一套更松。** 问题是 schema/流程，不是某一家模型；分模型策略会掩盖缺陷。

## 5. 改完后，怎样才算「没引入新问题」

用现有测试资产就能卡死边界：

| 回归 | 期望 |
| --- | --- |
| `ir_openclaw.yaml` 自检 | 仍通过（含单 flag 宽规则） |
| 人造「空条件 must_challenge」 | 自检失败，CLI 非 0，不生成「成功」报告 |
| 人造「destructive 单 flag deny」 | 通过（证明没误杀合法宽规则） |
| 离线 e2e C2 | 仍约 121428 / 8 / 1444，不出现 100%/0/0 |
| `--no-complete` 离线路径 | 行为不变 |

对 LLM 路径只断言：**恒真进不了 ok、IR YAML 存在、质量警告可测**；不断言「必须抽成 24 条」。

## 6. 建议的实施顺序（风险从低到高）

1. 判定规则「至少一个条件」+ 恒真自检 + `extracted_ir.yaml`（半天级，直接挡住本次故障）。  
2. C2 质量警告 + 警告时跳过补全（避免假收敛）。  
3. OpenClaw 章节隔离抽取，其它文档 fallback。  
4. 回译参考分（可不做）。

第 1–2 步不改变离线金样条和五项分析语义，是性价比最高、也最不容易伤 MustAllow 的切片。

如果你愿意下一步落地，我建议先写一份短 spec，然后只实现第 1–2 步。是否按这个范围做？
